# SpaceFox launch reminders — API feasibility memo

Captured 2026-11-15T16:10:56Z. Read-only research; no repository edits, installs, accounts, or paid/model API calls. Official web API references and Garmin HTML guides were read live. The Notifications and Backgrounding guide bodies were retrieved with Python stdlib HTTPS because the web parser failed. No physical FR165 or vibration test was performed.

## Decision

The full requested contract is **not established as implementable by a standalone FR165 watch face**: vibration every five minutes from T−60 to T−10, then every minute through launch, including screen-off/another-app operation, while suppressing Sleep Mode and DND.

There is an API-supported **system notification** path for watch faces and background services. It does not expose explicit vibration control or future scheduling. Background events cannot run more frequently than every 300 seconds. A foreground/onUpdate supplement can attempt one-minute notifications while callbacks occur, but cannot supply the missing one-minute screen-off/other-app scheduler. These are material capability limits, not a test gap that can be resolved by more host tests.

A limited, opt-in notification feature could be implemented if its product contract clearly acknowledges those limits. Do not label it guaranteed vibration reminders or claim the original request complete. If shipping requires the original behavior, retain feasibility evidence and leave delivery blocked on a different architecture/product scope.

## Original developer observations — risk evidence, not normative/current FR165 proof

- [FR165M screen-off callback report](https://forums.garmin.com/developer/connect-iq/f/discussion/414283/check-if-aod-is-enabled-screen-is-off): author observed gaps in onUpdate when AOD was disabled/screen off, and one-minute callbacks with AOD enabled. This directly warns against using general low-power API wording as a screen-off scheduling guarantee. It does not establish behavior of today's user's firmware.
- [Instinct 3 background notification bug report](https://forums.garmin.com/developer/connect-iq/i/bug-reports/instinct-3-solar-45mm-notifications-shownotification-from-a-background-service-shows-nothing-works-in-foreground): physical foreground notification reportedly vibrated; same background API reportedly showed nothing. This is another product, so do not generalize it as FR165 failure; it demonstrates why source/compiler/simulator support cannot establish physical alert behavior.

## Requirements for any explicitly limited implementation

1. Default off; opt-in menu wording must identify notifications and any screen/cadence limitations. API availability/firmware support must be checked rather than merely raising minimum API and assuming motor behavior.
2. Use one selected launch, stable launch ID, precise validated epoch time, nonterminal status and a bounded freshness policy. Unknown/NET/TBD/postponed/cancelled/stale launch times must not produce countdown notifications. A successful cached fetch is not inherently fresh enough at T−1.
3. Schedule slots are T−60,−55,…,−10, then −9,…,−1; include T0 only if the product contract explicitly includes a launch alert (21 slots with T0, 20 without). A late callback should select at most one currently eligible slot within an explicit lateness window, never loop over missed slots.
4. Persist a consumed/attempted slot identity keyed by launch ID + scheduled timestamp/revision + offset, shared by foreground/background. Persist before side effect for at-most-once attempts across reboot/reentrancy; this intentionally trades crash-time misses for avoiding duplicate notification bursts. An API call is not acknowledged physical delivery. Clarify reschedule semantics: changed launch time changes future schedule but must not replay every prior offset or create back-to-back alerts on updates.
5. At each attempt, suppress DND, vibration disabled, configured quiet interval, and any available live isSleepMode true. If the required DND/sleep/profile state is missing/null/invalid, **fail closed** for alerts; do not infer awake. Unknown legacy live sleep state means full manual-Sleep-Mode compliance remains unproved, even if configured hours are suppressed. Suppressed slots should be consumed/expired, with no wake-time catch-up.
6. Reuse and reconcile the app's existing Background temporal owner, refresh workflow, storage limits and lifecycle. No per-minute-background hack, timer spin, or phone message subscription can be described as equivalent without actual corresponding architecture and evidence.
7. Host cases should cover slot boundaries, non-minute-aligned timestamps, midnight/DST quiet intervals, unknown flags/profile, stale/terminal launches, delayed callbacks, suppression/no catch-up, reschedule, reboot, foreground/background duplicate attempts and storage errors. Simulator checks may prove compilation, callbacks and UI rendering only.
8. Physical FR165 checks are essential for notification visibility/vibration (foreground, AOD on/off, other app/activity active), notification settings, DND, scheduled sleep, manual Sleep Mode with DND both on/off, reboot and background timing. No such acceptance was obtained in this research.

## Handoff verdict

Supported: immediate OS notifications via API5.1 and guarded conservative suppression logic; five-minute background opportunities.

Unsupported/unproved: guaranteed vibration, guaranteed one-minute reminders when screen off/other app active, exact launch-second delivery, and reliable current FR165 live Sleep Mode state. An author/peer must preserve these boundaries and avoid publishing partial behavior as fulfillment of the original full request.
