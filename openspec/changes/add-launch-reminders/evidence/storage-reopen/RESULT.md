# SDK storage reopen

A disposable test UUID on the isolated network-none FR165 simulator used the actual `NativeStore`/`Application.Storage` and the production reminder owner, with controlled time and a fake notification sink. The first app process consumed a quiet slot and printed `REOPEN_SEED stored=true calls=0`; the launcher then timed out. The second process used the existing `RunInstalled.java` direct open path (`push=false`) for the same UUID and observed `persisted=true calls=0 duplicateSuppressed=true` without pushing a package. See [probe](Probe.mc.txt), [seed](seed.log) and [reopen](reopen.log). This is SDK application-process storage reopening, not physical watch power loss, a reboot or a device notification observation.

The first attempt to compile the direct-open Java helper inside the Linux container exited 127 because `javac` was absent. The same retained Java source was compiled using the already-installed host Java 11 compiler against SDK9.3, then executed in the task-owned container with its Linux SDK; no installation was performed. The first launcher ended with timeout exit 124 after its seed marker; the direct-open helper ended with exit 0 after its reopen marker. Neither exit represents a physical device reboot.
