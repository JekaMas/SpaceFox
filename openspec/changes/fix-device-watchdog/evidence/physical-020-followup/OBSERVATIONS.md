# Physical 0.1.20 follow-up

The owner reports 0.1.20 does not crash, but updates do not arrive, launch point and countdown do not appear, and LOW differs from the intended design. This is qualitative feedback, not a timed endurance pass or proof of the installed binary. The published PRG was previously transferred and read back exactly; physical version display and elapsed duration were not observed independently. USB was absent at the start of this follow-up.

On 2026-11-16 the actual public `/feed.json.txt`, referenced catalog and transfer descriptor returned HTTP 200; both immutable object digests matched. The selected Long March 2D launch at Taiyuan had source-coarse `HR` precision, which is insufficient for an exact countdown under the existing contract. This does not explain missing site/map point or establish device data delivery. Raw public capture is private at `/Users/jekamas/.codex/tmp/spacefox-live-followup-20261116/`.

The current `SpaceFoxView.updateForDisplayMode` admission-pending branch draws an abbreviated text screen even in LOW, so it cannot satisfy the specified LOW layout. Cause and repair remain under investigation; the physical gate remains open.

A fresh read-only USB snapshot after the reported failure identifies the watch as FR165 Music, but its current `GarminDevice.xml` no longer contains the prior SpaceFox AppId/StoreId/GBG81953.PRG entry (10 app entries versus 11 in the previous snapshot). Neither known staging name `SPACEFOX.PRG` nor `GBG81953.PRG` is visible in Apps. CIQ_LOG.YML is absent, and the available CIQ_LOG.BAK matches the old YML byte-for-byte. This does not establish which version produced the reported screen. App data/settings were not read because current metadata no longer confirmed their ownership. The new private snapshot is `/Users/jekamas/.codex/tmp/spacefox-physical-020-failure-20261116-lm4iz5js/`; previous snapshots remain untouched.

Source diagnosis: initial and warm `admissionPending` bypass the full AOD renderer, and the normal AOD has no default outline when context is absent. These are confirmed code paths, but not proof that either caused the physical screen. The temporary LOW-resource draft and its stock memory/visual observations are pending.

The scoped SpaceFox snapshot was later completed under explicit identity authorization: GBG81953.DAT, IDX, IMT and SET were copied into the same fresh private directory. No SPACEFOX-named app data were visible. The SET contains the exact default public feed URL. Application storage did not expose feed or marker keys as plaintext; no cache-state conclusion follows. Omission of the prior Store listing from GarminDevice.xml is not proof that a sideloaded build is absent or uninstalled.

The first SDK LOW resource smoke selected one test and passed in English and Russian and with no context, using a unit-test VM. It does not establish stock memory or image equivalence. The first stock-event observer launch was manually interrupted while connected but emitting no VM output, before a terminal signal; this remains inconclusive. A second observer launch displayed an IQ icon and an isolated CIQ log reported only `Permission Required`; no stack identifies its owner. Opening the simulator Settings menu then caused an owned GTK pixbuf warning and simulator segmentation fault. These are retained environment/observer observations, not a physical product root cause or passing cold pipeline.

A fresh-UUID FR165M SDK observer subsequently exercised the real public HTTPS endpoint in the actual background-service context. The live 5,660-byte feed returned HTTP 200; feed staging and `NativeBatch.begin` succeeded; the pinned catalog returned HTTP 200 and was stored; the foreground received background data and logged admission accepted. Callback heap samples were 32,984 bytes at feed and 29,976 bytes at catalog. The observer overrides only logging and uses the production service/app owners. This refutes background stage/batch failure for this finite simulator case, not the owner's physical-phone case or an all-device timing bound. The corresponding active frame showed Long March 2D, Taiyuan and a map point; the HR-precision countdown was unknown. The log and image are retained under `/Users/jekamas/.codex/tmp/spacefox-live-low-sdk-20261116/event/`.

The observer's earlier `Permission Required` was isolated to its own timer started in `getInitialView`, not to Communications: the native stack named `Timer.start` and `Probe.mc:18`. Removing that observer timer allowed the same true-service path to run. The previous GTK Settings-menu crash remains a simulator-environment observation.

The first catalog-exit follow-up used a fresh SDK service event and the same persisted pending batch. Feed polling was not due, so no second feed request was made; the service fetched the descriptor and remaining live objects with HTTP 200 and delivered the batch to foreground. A separate captured-current SDK test passed the same cross-event batch ownership and final closure check with 26 remaining objects. In a more intrusive visual probe that forced a LOW redraw on every HIGH frame even after admission, the completed artwork build subsequently OOMed in `NativeSfr.chunk`. This artificial HIGH/SFR/LOW-resource overlap is retained as a counterexample; it neither proves nor disproves normal lifecycle safety. A separate natural lifecycle transition through LOW during a pending SFR build and back to HIGH is required.

The direct short-wake SDK case passed with the same incremental parser retained through a simulated LOW draw and HIGH resume, and exact countdown seconds advanced across two frames. Its 161,864/162,032 byte before/after samples are from a unit-test VM, not stock device heap. A Russian forced-LOW visual on the live selected point shows map outline, point, weekday/date, clock, unknown coarse countdown and battery. It is a forced-draw observation, not a real display-mode transition.

The same live accepted and fully downloaded closure was reopened in the production view without the forced-LOW proxy or fixture arrays. It also terminated with an OOM at `NativeStore.read` → `NativeImmutable.raw` → `NativeSfrDecoder.chunk`; that is a directly reproduced stock-view software failure, not merely proxy overhead. As a targeted hypothesis, the adjacent performance lane identified the pixel-rest mask as LOW-only yet retained through HIGH. That lane's WIP was not merged; the draft here allocates that mask only for LOW and releases it on HIGH, retaining the same draw operation. Whether this is sufficient for this exact input remains under test.

With the mask change, the previously failing live closure completed in a production-view reopen: the later SDK frame showed the detailed selected rocket, Chinese flag, map and Taiyuan point; current app heap was 107.7/123.8 KiB, not an exact peak. The corresponding test-only lifecycle proxy then injected SFR start → LOW draw → HIGH wake and reproduced OOM when LOW and HIGH were invoked in one callback. A second injected sequence started a timer in HIGH and returned from the LOW callback before delivering the wake callback; it also OOMed at the same raster read after resumption (boundary samples 108,744 before LOW, 107,696 LOW, 107,176 wake, 108,800 resumed). This was not a simulator global display-mode change or physical sleep. Both failures remain retained. The next targeted draft removes redundant AOD map/font preparation in HIGH before SFR resumes; the map and mask remain prepared on entry to LOW. It is not yet qualified.

The additional HIGH cleanup (no eager AOD prefetch; immediately release LOW map/font/mask on HIGH/OFF) still failed the split-callback lifecycle at the same raster read. Paging LOW-only methods and explicitly releasing a cancelled job's unpublished decoder/DC/bitmap and partial result also failed that discriminator; before/LOW/wake/resume callback samples were 107,048/106,000/104,784/107,120 bytes. No claim of a passing SFR sleep/wake or of a precise OOM cause is made. The normal no-sleep stock frame and the failed lifecycle cases are both retained.

Targeted shard instrumentation located the failed read at the seventh map shard (4,044 bytes), with 118,304/126,784 bytes sampled immediately before it; cancellation had occurred while the root reader existed and before decoder construction, so decoder cancellation retention was not established as the cause. Paging the large `NativeSfrDecoder.oneRow` method preserved its code and pixel/integrity behavior and allowed the same split-callback lifecycle to complete: sampled 106,008 before LOW, 104,960 LOW, 103,744 wake, 110,120 resumed and 108,656 bytes at completed artwork. The production stock view on the same closure then showed the detailed rocket, flag, map and point with 104.4/123.8 KiB current heap. Neither sample is an exact peak or a physical-device result. The production view's earlier live active frame showed the selected facts and point before optional art completion.
