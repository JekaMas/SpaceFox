# Storage ownership inventory — intermediate D analysis

This is source accounting, not a measured device quota. Garmin SDK 9.3.0's local `doc/Toybox/Application/Storage.html` documents a device-dependent Object Store limit and a 32 KiB maximum per value. It exposes no key-enumeration API. Simulator file sizes below are one sample and cannot be added to source-level payload ceilings to obtain a physical-watch capacity.

| Current owner/category | Current key slots, excluding pre-existing orphan keys | Payload or semantic boundary |
| --- | ---: | --- |
| Immutable objects plus index | 56 + 1 | `NativeImmutable` accepts at most 56 indexed objects, each at most 4,096 UTF-8 bytes, and at most 229,376 indexed object bytes. The index is a separate value. |
| Batch head, pending and reference list | 3 | At most 40 selected refs / 114,688 declared transfer bytes; refs are metadata, not another copy of those object bytes. |
| Raster active/recovery and accepted/recovery markers | 4 | Two selected raster pins and two feed commit pointers, all separate structured values. |
| Three feed-slot headers and chunks | 3 + 48 | Each slot can have 16 chunk keys of at most 512 characters; an accepted complete feed verifies at most 8,192 UTF-8 bytes. Old/trailing or interrupted slot fragments do not share that accepted-feed total. Each chunk is bounded separately, with up to 2,048 UTF-8 bytes per 512-character slice checked by the reader. |
| Provisional feed marker, processed token and two banks | 2 + 32 | At most 16 positions per bank. The new cleanup removes unreferenced banks/tails after a verified marker write, best effort; an interrupted cleanup can still leave separately bounded fragments. A valid assembled feed is at most 8,192 bytes. |
| Provisional asset marker, processed token and two banks | 2 + 16 | Current production HTTP path writes immutable objects directly; the retained `stage("object",...)` seam accepts at most 4,096 bytes / 4,096 characters, hence at most eight 512-character positions per bank. Include its possible keys conservatively. |
| Publisher index and floors | 1 + 8 | Current publisher floor admission has an eight-namespace index; floors retain identity and replay authority. |
| Upcoming queues | up to 8 for current indexed writers | One derived queue per admitted pinned URL, each with at most three validated scene rows. New save checks the existing pin/index rather than evicting protected future facts. Earlier unindexed keys cannot be enumerated or honestly included in a universal count. |
| Reminder snapshot, control, comparison and consumed ledger | 4 | Current consumed ledger retains at most 16 actionable rows plus watermark. Unknown/corrupt state fails closed. |
| Attempt, transfer-ready and transfer-plan | 3 | Separate retry and derived policy/target values. |
| Selected field identities | 4 | Four source identities; settings properties are separately stored by the platform. |

The category sum is **195 possible named/indexed keys** under the explicitly stated current-writer/no-orphan assumption. It is not a total-store key or byte guarantee: older orphan keys are not discoverable through the SDK, platform serialization and key overhead are unspecified, current queue/text values have data-dependent size, and the per-device total quota is unspecified. The 56 / 229,376 immutable-object constants are only one category, not the whole store. A failed quota/write/readback must preserve accepted data; counting these maxima does not establish that every mathematical combination fits.

The [isolated frozen-fixture simulator sample](storage-sample.json) contained 83,480 bytes in the app `.DAT`, 2,008 in `.IDX` and 354 in `.SET` after the offline 19-object seed and before stock launch. PRG, debug XML and simulator system files are separate. It did not exercise eight URL queues, the fullest accepted feed, interrupted writes, a physical device or a measured platform quota. Those cases and current-source tests are still required.

The current-source [storage sequence](storage-sequence-native.log) passed 2/2 against the production `NativeTransfer`, `NativeIncoming` and `NativeCache` with an injected store: a failed marker write kept the prior fragment readable and accepted marker unchanged; an interrupted delete left the new fragment readable and a repeated stage reclaimed the unreferenced tail; active and recovery feed slots were protected, and a failed inactive-tail delete was safely retried without changing accepted or future facts. [Compiler/source receipt](storage-sequence-compile.json), [test source](StorageSequenceTests.mc) and [runtime/ini restoration](storage-sequence-restore.json) are retained. The separate actual eight-queue test exercises eight pinned URLs, ninth refusal, a failed queue write and corrupt-seal recovery. Injected failures do not establish an actual device-specific quota or universal fit; the 195-key/no-orphan scope and unindexed historic-key limit above remain explicit.
