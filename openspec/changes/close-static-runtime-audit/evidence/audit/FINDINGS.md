# Provisional findings

Audit scope is static source inspection only; no timing or heap measurements were made. Findings are provisional until caller, contract and peer review are complete.

## A01 — Unranked investigation: repeated map selection while optional artwork decodes

Trigger: HIGH mode, an accepted scene with a qualified point and an optional SFR build in progress or deferred. `SpaceFoxView.mc:394-396` runs a one-second clock timer in that fallback state; `:306-314` dispatches its redraw to `drawDecodingFrame`, which at `:338-343` reconstructs the map-coordinate byte array, scans its entries, and possibly scans additional AOD coordinates on every frame. `NativeAssets.mc:5` constructs the coordinate array when called. In contrast `SceneRenderer.mc:47-95` performs equivalent map/point selection during preparation and retains its result. Extra redraws may also occur; one second is the timer period, not a measured guaranteed device cadence.

The seconds clock itself and the lightweight presentation during SFR work are required, and releasing heavy renderer resources is intentional. The earlier current-integration peer explicitly recorded frame-local packed coordinates as part of the resource tradeoff (`evidence/current-integration-022/PEER.md`); no alternative has been shown to fit the same heap bound. This is repeated bounded work, but it is **not established to be unnecessary or a defect**. Investigate whether retaining only the small selected map identifier and projected point, invalidated on context change, can satisfy the same resource limits. Confidence: high for static repetition; cost and viability of a replacement are unmeasured. No severity is assigned without that evidence.

## A02 — P3: contradictory current countdown specifications

`specs/launch-schedule/spec.md:154-160` requires an inexact NET without a precision prefix, consistent with the latest explicit user instruction to remove `~`. In the same current change, `specs/watchface/spec.md:168-172` still requires an estimated prefix; `openspec/changes/fix-device-watchdog/specs/runtime/spec.md:82` also explicitly requires `~T−/~T+`. These requirements cannot both govern the same inexact target without clarification. This is a specification inconsistency, not a claim that the implementation displays a tilde. Recommendation: reconcile the obsolete prefix text with the newer approved no-prefix policy, retaining source precision and exact-reminder distinction. Confidence: high for the textual conflict; current display owner was reviewed statically and does not add the superseded prefix.

## A03 — P3: selected freshness is recomputed twice per normal active redraw

For a normal accepted packet whose `presentation` remains the selected `context`, `SpaceFoxView.mc:385-387` calls `packet.advance(now)`, then `snapshotAt(now)`. `NativeTrustedSnapshot.mc:60` implements the former by calling `presentation.advanceFreshness(now)`; `SpaceFoxView.mc:126-128` calls `context.advanceFreshness(now)` again. The same `now` and same `SceneContext` therefore traverse the same stale-policy arithmetic twice on that redraw. The active face needs seconds, and source freshness is authorized; the duplicate calculation is not needed to provide a second clock or separate freshness source. No Storage or network access is involved in these calls and no timing or battery impact was measured. Recommendation: consolidate the freshness update at one owner boundary while preserving successor selection, sticky stale semantics and stale value propagation. Confidence: high for the stated same-context path; alternate rollover contexts require care. Peer independently confirmed the same-context path, sticky stale arithmetic and successor-selection limitation; see `peer/CROSSCHECK.md`.

## A04 — P3: illustrative preview constructs both date formatters on every second tick

While the embedded `prototype/mission.js` root remains connected, its interval at `:158` invokes `renderClock()` every 1,000 ms. That function creates new `Intl.DateTimeFormat` objects for both local time and date at `:63-66` even when locale and date have not changed. The preview's countdown tick and widget cleanup are separately required by the prototype contract; constructing both immutable formatters anew is not required for those behaviors. It affects the illustrative browser widget only, not the Garmin app. Recommendation: retain formatters keyed by locale/options and update date only when its displayed value changes, preserving the fixed demo timezone. Confidence: high for repeated construction; actual performance impact is unmeasured.

## A05 — P3: unused former feed timestamp parser remains in production source

`watchface/monkey.jungle:2` includes all of `watchface/source`, including `NativeSourceTimes.mc:1-62`. In the current production source tree, `nativeSourceIso` and `nativeUtcDay` have no callers outside their own file; the only found callers are diagnostic test fixtures and historical retained source. The current `NativeTrustedSnapshot.mc:1-42` receives projected numeric timestamps instead. Thus the former text ISO validation and its helper chain add source and maintenance complexity despite the retired on-watch raw-feed protocol. This does not establish generated binary size or execution cost: the compiler may remove unreachable code. Recommendation: move any still-needed diagnostic helper to the test fixture and remove the unused production owner after checking generator/source-closure dependencies. Confidence: high for direct production-source references inspected; compiler elimination and external generated-source dependencies remain unmeasured.

## A06 — Unranked investigation: reminder owner accepts two persisted snapshot shapes

`LaunchReminderForeground.mc:13-14` preserves `since` from either the current `rows` array or an older flat `{id,target,since,...}` dictionary, while `LaunchReminder.mc:58-60` returns that flat dictionary directly when `rows` is absent. The only production writer inspected writes the `rows` shape at `LaunchReminderForeground.mc:20-21`. Current validity, source/sequence, quiet-state and durable consumed-slot guards continue to apply to the flat branch; see `peer/CROSSCHECK.md`. Thus the older-form reader is reachable when such a saved value exists and duplicates the selected-reminder interpretation. The latest recorded development decision rejects adding legacy compatibility layers; this existing stored-state reader may have a continuity rationale, and no explicit decision banning this particular shape was found. An authority gap alone does not establish an unapproved fallback. Recommendation: resolve the retained on-device-state implications and the no-legacy instruction before removing the two old-shape branches; do not silently discard pending reminder state or weaken current reminder eligibility. Confidence: high for the two code paths and present writer; presence of any affected device state and original compatibility decision were not observed. The peer independently confirmed current eligibility, quiet-state and deduplication guards still apply; no severity is assigned without a decision on state continuity.

## A07 — Unranked investigation: regenerated world segments on fallback frames

`watchface/source/generated/FallbackWorld.mc:5-10` creates its packed line-segment byte array inside each `draw` call. The scene renderer calls it for an unmatched world point (`SceneRenderer.mc:146`); `SpaceFoxView.mc:343,369` also calls it in decoding/clock fallback. While the foreground fallback clock owns its 1,000 ms timer (`SpaceFoxView.mc:394-396`), those fallback redraws can repeatedly recreate the same static geometry. The runtime needs correct fallback map and seconds; the `:extendedCode` design and `current-integration-022/INTEGRATION.md` intentionally page and pack geometry to protect the SFR memory reserve. No alternative is proven to stay within that reserve, and callback latency, allocation cost and device power are not measured. Consider a bounded reuse option only after its lifetime/heap impact is measured. This is an investigation, not a demonstrated defect or reason to remove the required map.

## A08 — P3: open task list retains superseded schedule strategies

The latest explicit cadence decision and `specs/launch-schedule/spec.md:21-32,69-74` require healthy hourly requests, first connected opportunity on failure/no future, and offline five-minute checks. Nevertheless `tasks.md:30-31` still asks for 60/15-minute due checks, optional fast mode and adaptive/window-based polling as open work. The original `proposal.md:19-21` and `design.md:188-204,245-255` also describe those old strategies without a nearby supersession note, and `docs/SCHEDULE_CORE.md:103-112,120-123`, `docs/PUBLISHER_STATE.md:64-73`, `docs/AGENT_SETUP.md:57-62`, and `docs/PROVIDER_PIPELINE.md:70-76,88-89,263-264` still present near/fast cadence, HTTP backoff or fast bootstrap as current policy, while the later 0.2.4 checklist states the consolidated policy. This can direct a future implementer or reviewer to restore explicitly removed behavior or demand obsolete tests. Recommendation: reconcile the open task text and mark the original proposal's cadence historical/superseded, preserving historical receipts and the separate current freshness thresholds. Confidence: high for the documented contradiction; this is not a claim that the current runtime uses the old cadence.

## A09 — P3: watchdog spec retains retired staged-feed admission as an active requirement

`openspec/changes/fix-device-watchdog/specs/runtime/spec.md:36-63` requires provisional raw-feed token cooldown, authenticated chunks, semantic/record hash verification and strict raw/inverse restore. The later trusted-schema cutover explicitly retired that on-watch raw-feed path; the current `spacefox-watchface/specs/launch-schedule/spec.md:79-97` instead specifies direct JSON snapshot and interrupted pointer recovery, as also reflected by `NativeTrustedSnapshot.mc` and `FeedService.mc`. Both remain written as active SHALL requirements without a supersession marker. This can cause maintainers to reintroduce retired duplicate admission or reject the current approved path, but does not show that such code is executing. Recommendation: retain historical rationale/evidence while explicitly superseding only the obsolete raw-feed admission clauses, preserving clock, atomic snapshot, independent visual and lifecycle requirements. Confidence: high for text and current owner mismatch; independent peer statically cross-checked FeedService.mc:30-43 and NativeTrustedSnapshot.mc:27-33. No historical test was executed.

### A10 — P3: Current-labeled delivery documents omit the separate watch schedule route

- Trigger: an operator uses the sections labeled “current” to reason about the watch schedule request or its schema.
- Evidence: `docs/EFFICIENT_STORAGE.md:5`, `docs/WORLD_CLOUD_INTEGRATION.md:10`, and `docs/NATIVE_RASTER_V3.md:3–7` call schema-3 `/feed.json` the “current public wire format” or “current feed.” These statements describe a real published root but omit the separate watch schedule request. The later active schedule contract requires JSON `watch.json` at `openspec/changes/spacefox-watchface/specs/launch-schedule/spec.md:79–83`, and `watchface/source/FeedService.mc:30–34` requests it. The SFR asset/legacy publisher root is a separate dependency; this finding does not say that every `/feed.json` reference should disappear.
- Effect: source and operations guidance can be confused with an older watch acquisition protocol. This is incomplete documentation, not an assertion that `/feed.json` is unavailable or an observed wrong HTTP request.
- Recommendation: qualify the old format sections by their historical source and describe the current schedule projection and independently retained artwork route precisely. No runtime change is recommended by this finding alone.
- Confidence: high for the quoted contradiction; no endpoint or device operation was performed in this audit.
