I checked nonempty finite glyph-line observations, visible/clipped flags, circular glyph fit, line overflow, finite graphic boxes, minimum font thresholds, minimum separation between measured blocks and marker halos, body width and contrast. The minimum observed separation is **4 px**, exactly the frozen floor. The rocket body is **12 px** wide. Independently recomputed minimum text contrast is about **12.82:1**, minimum measured essential-graphic contrast about **6.06:1**, and marker contrast about **5.02:1** against the declared worst-case backgrounds. Opaque metadata plates and the actual palette make the contrast assumption inspectable; these are browser proxies, not measured eyesight.

Font size is not glyph height: the clock’s measured glyph height in the control is about 57.46–58.48 px despite an 80 px font size; site glyphs are about 16.17–21.23 px, and metadata about 12.28–17.39 px. This resolves the earlier em-versus-ink ambiguity without claiming a physical readability threshold. The narrowest gaps and small icons still require device/user validation if a native implementation follows.

The renderer uses the same D3 projection for the map/land/grid and site point (`prototype/qualification/renderer.js:29`). It translates that shared projection to a reserved marker anchor rather than moving the marker separately (`renderer.js:30`). Raw observations do not store a model identifier, so model routing is source-inspected; independent silhouette recognition is **not** claimed.

The new Q4-33 actually changes the layout grammar: two stable rows of two field pairs, a lower connected Earth limb and a different mission anchor (`renderer.js:16`, `renderer.js:37`). Compared with the upper-right globe of Q4-11 and the wide mission-centered map of Q4-21, each pair differs in at least two structural dimensions, not merely color or projection. They remain variants of one coherent typographic family, not evidence of three radically unrelated design languages.

## AOD evidence

`aod-pixels.json` retains 15 actual canvas-count receipts: five representative scenes for all three final candidates, with dimensions, clock/countdown, candidate and scene labels. I independently counted the native circular pixel-center denominator as **119,488**, verified every reported numerator/denominator/ratio and candidate binding, and inspected the source path from 390×390 `getImageData` to nonblack-pixel counting (`renderer.js:53`, `core.js:31`). The observed ratios are **2.818–4.464%**, below the project’s 8% target. My receipt is `aod-independent-check.json`.

I subsequently decoded all five exported native 390×390 PNG frames independently using only Python’s standard library, validated their chunk CRCs, reconstructed the pixel filters and counted every nonblack visible pixel within the circular screen. Counts are exactly 4,130 / 3,367 / 5,111 / 5,334 / 4,808, each over 119,488; all agree with the 15 candidate/frame receipt entries. The implementation and results are `aod-raster-audit.py` / `aod-raster-independent-check.json`. This does not import the production counter. All three variants share this reduced AOD composition; `aod-raw-export.json` records equality of their frame buffers. The JPEG previews are not the source of the exact pixel counts. None of this proves native Garmin AOD compliance, brightness, burn-in behavior, battery consumption or physical legibility.

## Remaining claim boundaries

No unresolved material technical defect was found in the **declared finite browser benchmark** after these repairs. The full readable strings are proved for these supplied scenes, not exhaustively for every possible string of the same grapheme length, every locale or every real launch feed. A fresh holdout has not been restored by reusing the repaired control. The visual re-review after feedback is likewise informed regression, not a new naive first exposure.

The area score still measures available geographic window area rather than geographic recognition, human comprehension or glance speed. It must not be used to claim a scientifically measured design optimum. Source code, image review and bounded detector results now justify presenting three concrete browser proposals. They do not justify claiming a finished watch face, native fonts/animation behavior, model recognition without labels, live schedule updates, child preference or superiority on a physical Forerunner 165.

Within those boundaries, no further unbounded layout generation is warranted by the technical evidence. The useful next choice is a user preference among the three proposals and, if native implementation is authorized later, a real-device typography and glance-reading check.
